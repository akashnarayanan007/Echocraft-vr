# ECHOCRAFT VR — Competition Engineering & Quality Rules

Project: ECHOCRAFT VR — The Last Light
Competition: Meta VR Start Developer Competition 2026
Track: Entertainment / Division: New Experience

These 10 strict guidelines govern all development, refactoring, visual enhancement, testing, and delivery in this workspace.

---

### Rule 1: Production Branch Protection
- `main` is the deployed production release branch. Never modify, commit directly to, force-push, or deploy from `main` without explicit confirmation and full QA sign-off.
- All development and experimentation must occur on designated feature/competition branches (`competition-final`).

### Rule 2: Meta IWSDK v1.1.0 Conventions Preserved
- `iwsdk.config.json` is the sole project authority, not `vite.config.ts`.
- Never import `three` directly from npm in application code; always import Three.js through `@iwsdk/core` (`import { ... } from '@iwsdk/core'`).
- Procedural assets live in `src/scene-assets/*.scene-asset.ts` and must be deterministic and side-effect free.
- Scene composition lives purely in JSON under `public/scenes/*.iwsdk.scene.json`.
- Allocate objects in `init()` as class properties, never dynamically inside `update()` to preserve 72-90 fps VR frame budgets.

### Rule 3: Strict Asset Licensing & Provenance Tracking
- Every external model, texture, audio clip, or font must be tracked in `ASSET_CREDITS.md` with source URL, author, and permissive license (CC0, CC-BY, MIT, etc.).
- Never commit proprietary, non-commercial, or uncredited assets.

### Rule 4: Zero Toleration for Fabricated Evidence
- Never fabricate test logs, simulation results, or screenshot outputs.
- All reported measurements and screenshots must be generated by actual execution tools (Playwright, IWSDK CLI, Chrome DevTools).

### Rule 5: Honest Emulation Reporting (No Fabricated Headset Claims)
- Testing in desktop XR emulation (IWER) must always be stated accurately as "Desktop Quest WebXR Emulation".
- Never claim physical Meta Quest headset verification unless hardware is physically connected via USB/ADB and verified via `npx @iwsdk/cli xr status` or `runtime status`.

### Rule 6: Mandatory Visual Evidence for Graphics Changes
- Any visual overhaul, lighting adjustment, or diorama styling update must be verified with high-resolution screenshot captures (1920x1080 and 1366x768).
- Screenshots must be reviewed to verify framing, lighting contrast, text readability, and absence of visual clipping.

### Rule 7: Gameplay & Interaction Regression Testing
- Any modification to materials, geometry, or transform hierarchy must be regression-tested against:
  1. Pointer/ray selection of memory fragments.
  2. Sequential socket snapping (Warmth -> Life -> Hope).
  3. World expansion and sunrise transition triggering.

### Rule 8: Meta Quest Standalone Performance Standards
- Target framerate: 72 fps to 90 fps (11 ms to 13.8 ms budget).
- Minimize draw calls: prefer instancing or merged geometries where applicable.
- Avoid dynamic memory allocations (`new Vector3()`, `new Color()`) within per-frame systems.
- Texture resolutions should remain bounded (<= 2048x2048) to prevent mobile XR GPU memory exhaustion.

### Rule 9: Desktop Pointer & Keyboard Fallback Preservation
- Maintain full accessibility on desktop browsers for competition judges evaluating without VR headsets.
- Retain mouse click-and-drag orbit controls, raycaster fallback, and keyboard shortcuts (`1`, `2`, `3` for socket placement; `E` for XR toggle).

### Rule 10: Continuous Verification & Changelog Maintenance
- Before claiming completion of any task:
  1. `npm run typecheck` (0 TypeScript errors required).
  2. `npm run lint` (0 ESLint errors required).
  3. `npm run test:smoke` (automated headless browser render verification).
  4. `npm run build` (production Vite bundling verification).
- Document changes in `CHANGELOG.md` or git commit messages.
